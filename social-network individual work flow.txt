WebSocket contract and message types (minimal, stable)
Handshake: client opens ws://.../ws and sends cookie/session token in the initial HTTP request (or Sec-WebSocket-Protocol header). Server validates against sessions table and returns {"type":"connected","user_id":123}.

Client → Server messages

{"type":"send_message","to_id":45,"text":"hi","temp_id":"abc123"}

{"type":"send_group","group_id":7,"text":"hello group","temp_id":"gtemp1"}

{"type":"ack","message_id":789}

Server → Client messages

{"type":"message","message":{...}} — new 1:1 message

{"type":"group_message","message":{...}} — new group message

{"type":"notification","notification":{...}} — generic notification

{"type":"error","code":401,"message":"unauthorized"}

Notes

Include temp_id so frontend can reconcile optimistic UI with DB id.

Always include created_at and sender_id in message payloads.

Keep message payloads compact; frontend can fetch full history via REST if needed.

WebSocket hub design and integration points
Hub responsibilities: manage connections, map user_id -> connection(s), route messages, broadcast to group members, and persist messages to DB.

Auth: validate session cookie on upgrade using sessions table; reject if expired.

Routing:

For 1:1: persist message, then SendToUser(to_id, payload). If recipient offline, only persist and create notification.

For group: verify group_members membership, persist group_messages, then broadcast to all connected members.

Notifications: any action that should notify a user (new message, group invite, event) writes a notifications row and pushes a WS notification event to the target user if connected.

Concurrency: use channels per connection and a central goroutine for hub events; avoid blocking DB calls on the WS goroutine — use worker pool or background goroutine to persist and create notifications.

Security, testing, and deployment checklist
Security

Validate session on WS upgrade; reject if not found or expired.

Authorize group actions by checking group_members.

Sanitize text inputs; limit message size.

Rate limit sends per user to prevent spam (simple token bucket).

Testing

Unit tests for DB queries and notification creation.

Integration test: simulate two WS clients, send message, assert delivery and DB row.

Load test: simulate many WS connections to validate hub scaling.

Deployment

Expose WS endpoint on backend container; if behind reverse proxy (Nginx/Caddy), ensure Upgrade headers are forwarded.

Use Docker Compose to run frontend + backend + sqlite volume.

Add health endpoint /healthz for container orchestration.
